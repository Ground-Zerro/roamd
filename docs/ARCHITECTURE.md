# Устройство демона

> Документация для версии **roamd 1.2.0-r2** (веб-интерфейс **luci-app-roamd 1.2.0-r1**).
>
> Проект передан [freenetic](https://github.com/unisequence/freenetic) — дальнейшее
> развитие идёт в его рамках.

Реализация `roamd`: модули, работа с hostapd, ubus-интерфейс, подкоманды и данные. Правила
принятия решений описаны в [HOW_IT_WORKS.md](HOW_IT_WORKS.md), Mesh Wi-Fi-система — в
[MESH.md](MESH.md), опции — в [CONFIGURATION.md](CONFIGURATION.md).

## Общая схема

```
                 ubus
  ┌──────────────────────────────┐
  │  hostapd.<интерфейс> (2.4)   │◀── события probe / auth / assoc / disassoc,
  │  hostapd.<интерфейс> (5)     │    beacon-report
  └──────────────────────────────┘
        ▲                  │
        │ вызовы           │ события
        │                  ▼
  ┌──────────────────────────────┐        ┌────────────────────────┐
  │            roamd             │───────▶│ /etc/config/wireless   │
  │  bss ─ sta ─ policy ─ pair   │ libuci │ /etc/config/roamd      │
  │  provision ─ mesh_*          │        └───────────┬────────────┘
  └──────────────────────────────┘                    │ network reload
        │           │                                 ▼
        │ ubus      │ uloop_process               netifd → hostapd
        │ "roamd"   ▼
        │     roamd <подкоманда>  ── SSH / HTTPS ──▶ узлы mesh
        ▼
  luci-app-roamd
```

Демон — однопоточный цикл событий `uloop`. Опрос узлов, сборка профиля, сверка, перевод
клиентов и раздача соседей идут прямо в нём: канал управления построен на `libuclient`
с `ustream-ssl`, поэтому запросы к узлам не блокируют цикл. Длительные операции —
захват, освобождение, обновление, поиск кандидатов и подготовка устройства — вынесены
в подкоманды того же бинарника: демон запускает их как дочерние процессы и отслеживает
через `uloop_process`. Внешние утилиты нужны только там, где без них нельзя: SSH-клиент
для первого входа на устройство и пакетный менеджер на самом устройстве.

**Главный цикл не блокируется.** hostapd ждёт ответа демона на уведомление о кадре `auth` или
`assoc` около 100 мс и, не дождавшись, пропускает клиента — проверка допуска в это окно не
действует. Поэтому запросы к hostapd в цикле опроса асинхронные, свои методы ubus демон
вызывает напрямую, а не через ubus, служебные ключи и сведения о пакетах кешируются, а
синхронные вызовы hostapd ограничены по числу за цикл.

## Запуск и остановка

1. `main()` обрабатывает подкоманды `roamd apk-index <packages.adb>` (печатает
   `имя версия размер хеш`), `roamd apk-block <пакет.apk>` (отдаёт первый ADB-блок, чей SHA256
   указан в индексе) и `roamd crypt` (читает пароль из stdin и печатает хеш SHA-512 в формате
   `crypt`, со случайной солью — для входа `rpcd` на узле).
2. Загружается конфигурация. При `enabled=0` процесс завершается.
3. После подключения к ubus регистрируется объект `roamd`, находятся точки hostapd,
   выполняется автонастройка Wi-Fi и запускается mesh-часть (`mesh_start()`).
4. При остановке журнал переходов и реестр клиентов сбрасываются на диск.

Init-скрипт запускает демон под procd с `respawn` и регистрирует `procd_add_reload_trigger`
на конфигурации `roamd` и `wireless`. `reload` вызывает `ubus call roamd reload`: конфигурация
перечитывается без перезапуска процесса и без разрыва соединений.

## Работа с hostapd

### Обнаружение точек

При старте — `ubus_lookup("hostapd.*")`, далее подписка на событие `ubus.object.add`:
появление и исчезновение интерфейсов (например, после `wifi reload`) обрабатывается на лету.

Для каждого BSS отправляются:

* `notify_response {notify_response: 1}` — hostapd ждёт ответа демона на события
  `probe`/`auth`/`assoc` и использует возвращённый код как статус кадра;
* `bss_mgmt_enable {neighbor_report, beacon_report, bss_transition}`.

Если hostapd не ответил вовремя (так бывает сразу после загрузки), включение повторяется в
каждом цикле опроса, пока не пройдёт.

### Цикл опроса

Каждые `poll_interval` (2 с) для каждого BSS параллельно уходят запросы:

1. `get_status` — SSID, BSSID, частота, канал, класс операций, состояние.
2. Для управляемых BSS — `get_clients`: подключённые, их сигнал, HT, поддержка Beacon Report
   (`rrm`) и BSS Transition (бит 19 `extended_capabilities`).
3. `rrm_nr_get_own` — собственный Neighbor Report, пока он не получен.

Когда вернулись все ответы:

4. `rrm_nr_set` — точкам с тем же SSID передаются Neighbor Report соседей (локальных и
   точек Mesh Wi-Fi-системы), не больше 8. Список отправляется при изменении отпечатка и не
   реже раза в минуту.
5. Прогон политики.
6. Удаление записей клиентов старше `age_time`.

Запросы асинхронные (`ubus_invoke_async`); завершение каждого фиксирует `complete_cb`, который
приходит при любом исходе, в том числе при ошибке. Пока запросы в полёте, таймер опроса BSS служит
предельным сроком — 500 мс: не дождавшись ответа, демон отменяет запросы и закрывает цикл. Так
зависший hostapd одной точки не задерживает ни остальные точки, ни ответы на уведомления о
кадрах. При исчезновении BSS запросы в полёте отменяются.

### Источники данных о сигнале

| Источник | Что даёт |
|---|---|
| События `probe` / `auth` / `assoc` | RSSI в том диапазоне, где клиент подал кадр |
| `get_clients` → `signal` | RSSI подключённого клиента в текущем диапазоне |
| `beacon-report` | RSSI другого диапазона, измеренный клиентом: `rcpi / 2 − 110`, RCPI от 200 отбрасывается |

Оценок «на глаз» нет: если свежих измерений другого диапазона нет, клиента в него не переводят.

### Точки входа политики

`roam_policy_allow()` вызывается из обработчика `probe`/`auth`/`assoc`. Возврат `false`
заставляет hostapd ответить кодом 17. Первая проверка — `roam_admit()`: разрешены ли клиенту это
устройство и этот диапазон; затем пороговая логика. Правило клиента проверяется на всех трёх
кадрах и на каждом устройстве системы одинаково — независимо от того, есть ли у устройства
второй диапазон. Правило диапазона, который недоступен ни на одном устройстве системы, не
применяется нигде.

`roam_policy_run()` вызывается из цикла опроса для каждого BSS. Сначала отключает клиентов,
которым `roam_admit()` запрещает это устройство или диапазон, — сразу, без удержания и без счёта
попыток перевода; такие отключения пишутся в журнал отдельными событиями. Затем запрашивает
Beacon Report при нехватке данных — не больше 4 запросов на точку за цикл, остальные клиенты
получают их в следующих циклах, — и принимает решение о переводе в `sta_should_leave()`. Число и частоту запросов ограничивает
`roam_policy_can_steer()` — та же проверка стоит в межузловом `mesh_node_steer()`.

Перевод — `bss_transition_request` с Neighbor Report цели и флагом `abridged`, без
`disassociation_imminent`. Клиента без 802.11v при `allow_kick=1` отключает `del_client` с
`ban_time = deny_time`.

**Параметры `bss_transition_request`.** hostapd читает `mbo_reason`, `cell_pref` и
`reassoc_delay` из неинициализированных переменных, если их не передать, и отвечает
`Invalid argument`. Демон всегда передаёт все три поля явно; `reassoc_delay` обязан быть нулём
без `disassociation_imminent`.

## Автонастройка беспроводной сети

`roam_wireless_apply()` проходит по включённым секциям `wifi-iface` в режиме `ap` и приводит
опции к состоянию, заданному в `/etc/config/roamd`. У сети со снятым флажком роуминга
(`wifinet.roaming=0`) все три механизма выключаются — 802.11k, 802.11v и 802.11r:

| Опция `wireless` | Значение |
|---|---|
| `ieee80211k`, `rrm_neighbor_report`, `rrm_beacon_report` | `neighbor_reports` |
| `bss_transition`, `wnm_sleep_mode` | `bss_transition` |
| `ieee80211r` | `fast_transition` и шифрование семейства WPA2/WPA3 (`psk2`, `psk-mixed`, `sae*`, `wpa2*`, `wpa3*`, `wpa-mixed*`) |
| `ft_over_ds` | `ft_over_ds` при включённом FT |
| `ft_psk_generate_local` | `1` для WPA2 с общим паролем (`psk*`), `0` для WPA3 и WPA-Enterprise |
| `mobility_domain` | заданный `mobility_domain` или хеш FNV-1a от SSID, свёрнутый до 16 бит |
| `nasid`, `pmk_r1_push`, `r0kh`, `r1kh` | WPA3 и WPA-Enterprise: идентификатор устройства; держатели ключей поимённо — BSSID и идентификатор каждой точки системы с общим `mesh.ft_key`, `pmk_r1_push=1`; пока списка держателей нет (одиночный роутер) — универсальная запись и `pmk_r1_push=0` |

Запись и `network reload` выполняются только если хотя бы одно значение изменилось. Кроме
запуска и `reload`, функция вызывается через 2 секунды после появления нового BSS: сеть,
созданную мастером LuCI или вручную, демон дооснащает без перезапуска, а повторный проход не
находит отличий и не зацикливается.

## Проверка пары

`roam_pair_evaluate()` вызывается из метода `status` и для каждого BSS выставляет битовую
маску причин. Живая часть берётся из состояния демона (есть ли парная точка, управляется ли
BSS, получен ли Neighbor Report), конфигурационная — из `/etc/config/wireless`: все `ap`-секции
с тем же SSID сравниваются между собой. Группировка идёт по SSID — ровно по тому признаку,
по которому клиент считает точки одной сетью.

| Код | Смысл | Уровень |
|---|---|---|
| `not_managed` | BSS не управляется службой | роуминга нет |
| `no_peer` | нет точки другого диапазона с этим SSID | роуминга нет |
| `disabled` | одна из точек выключена | роуминга нет |
| `encryption` | разные типы шифрования | роуминга нет |
| `key` | разные пароли | роуминга нет |
| `network` | точки в разных сетях (мостах) | роуминга нет |
| `no_11k` | 802.11k выключен | не в полную силу |
| `no_11v` | 802.11v выключен | не в полную силу |
| `fast_transition` | 802.11r или mobility domain настроены несогласованно | не в полную силу |
| `no_neighbor_report` | точки ещё не обменялись Neighbor Report | не в полную силу |

В `status` это отдаётся как `state` (`ok`, `degraded`, `broken`) и список кодов, которые
LuCI переводит на язык интерфейса.

## ubus-интерфейс

Объект `roamd`. Колонка «Доступ» показывает, через какой ACL метод доступен снаружи:
**LuCI** — `luci-app-roamd.json` (чтение или запись), **канал** — группа `roamd` для входа
контроллера на узел. Методы без отметки вызываются только локально с правами root.

| Метод | Аргументы | Роль | Доступ | Назначение |
|---|---|---|---|---|
| `status` | — | обе | LuCI, канал | включённые механизмы, роль, точки доступа с состоянием пары и клиентами |
| `config` | — | обе | — | действующая конфигурация: все опции `opts[]` с учётом умолчаний |
| `reload` | — | обе | LuCI, канал | перечитать конфигурацию, дооснастить Wi-Fi, перезапустить mesh-часть, раскатать профиль |

| `mesh_status` | — | обе | LuCI, канал | контроллер: счётчики, сам контроллер, члены с живым состоянием, настройки MESH, текущая задача, точки `self_aps`, готовность зависимостей. Узел: контроллер и возраст контакта, настройки |

| `mesh_member_remove` | `id`, `reset?` | контроллер | LuCI | удаление узла; `reset: "1"` — со сбросом устройства |
| `mesh_client_update` | `mac`, `band?`, `alias?`, `nodes?` | контроллер | LuCI | правило клиента: диапазон (`2.4`, `5`, `both`), имя, разрешённые узлы через запятую (пусто — все) |
| `mesh_client_forget` | `mac` | контроллер | LuCI | удалить клиента из реестра и его правила |
| `mesh_network_update` | `ssid`, `roaming` | контроллер | LuCI | флажок роуминга у сети; применяется сразу — и к точкам контроллера, и к узлам при ближайшей раскатке |
| `mesh_profile` | — | контроллер | внутренний | профиль для узлов в том виде, в каком он уходит по каналу |
| `mesh_settings` | `backhaul_enabled?`, `backhaul_ssid?`, `backhaul_key?`, `wifi_shutdown?`, `node_ui?`, `backhaul_delta?`, `backhaul_min_signal?`, `auto_update?`, `auto_update_every?`, `auto_update_unit?`, `pkg_url?`, `controller_name?` | контроллер | LuCI | запись секции `mesh`, перестройка транспорта, таймера и раскатка |
| `mesh_log_ingest` | `id`, `node`, `events` | контроллер | — | приём событий узла из периодического прохода |
| `mesh_apply` | профиль | обе | канал | применить профиль контроллера |
| `mesh_report` | — | обе | канал | живое состояние устройства (раздел ниже) |
| `mesh_diag` | — | обе | канал | снимок для разбора неполадок без SSH: версии, конфигурации, адреса, мост, сервисы, объекты hostapd, хвосты журналов |
| `mesh_steer` | `mac`, `neighbors?` | обе | канал | запрос 802.11v клиенту с переданными кандидатами |
| `mesh_drop` | `mac` | обе | канал | удалить станцию, ассоциированную на другом устройстве |
| `mesh_neighbors` | `neighbors: [{bssid, ssid, nr}]` | обе | канал | принять карту точек системы и обновить Neighbor Report |

Методы, меняющие состав системы и правила, при роли `node` отвечают `Permission denied`.

### Отчёт устройства

`mesh_report` содержит: роль, `member_id`, `controller_id`, версию ОС, архитектуру, версии
пакетов `roamd` и `luci-app-roamd`, время работы; `clients[]` (MAC, диапазон, сигнал,
скорость, стандарт, ширина, потоки, шифрование, трафик, время ассоциации, признак `wired`);
`heard[]` (необслуживаемые станции со свежим сигналом); `connection`, `uplink_band`, `via`;
применённый профиль `profile`; точки `aps[]` с hex-элементом Neighbor Report; последние 100
событий журнала.

## Подкоманды

Вспомогательных скриптов в пакете нет: длительные операции — точки входа того же
бинарника. Демон запускает их как задачи, и их же можно вызвать вручную.

| Подкоманда | Где выполняется | Назначение |
|---|---|---|
| `roamd discover` | контроллер | поиск кандидатов в сегменте LAN: соседи через netlink, проверка доступности SSH до попытки входа, опрос устройства, наличие пакета под его ветку и архитектуру |
| `roamd acquire <адрес> <задача>` | контроллер | захват устройства: проверка, доставка пакетов, роль, перевод в подсеть контроллера, служебные ключи и канал управления |
| `roamd release <id> <задача>` | контроллер | сброс узла к заводским и удаление из системы вместе с резервом адреса |
| `roamd node-update <адрес> <задача>` | контроллер | переустановка пакетов на узле |
| `roamd self-update <задача>` | контроллер | обновление пакетов самого контроллера |
| `roamd autoupdate [nodes] <задача>` | контроллер | автообновление: сначала контроллер, затем узлы |
| `roamd deps-ensure [need]` | обе роли | доведение устройства до полного `wpad` с 802.11v; с аргументом `need` только печатает, чего устройству не хватает |
| `roamd net-apply <мост> <адрес>` | узел | перезапуск сети при захвате со сторожем отката по доступности контроллера |
| `roamd apk-index`, `apk-block`, `crypt` | обе роли | разбор индекса `apk` и хеш пароля без внешних утилит |

Ход задачи пишется построчно в `/var/run/roamd/acquire/<задача>` в формате
`шаг<таб>состояние<таб>текст`; эти же строки отдаёт `mesh_acquire_status`.

Опрос узлов, сборка и раскатка профиля, сверка, перевод клиентов, раздача Neighbor Report,
режим «тихой точки» и сканирование транспорта выполняются внутри демона, без отдельных
процессов.

## Данные в памяти и на диске

| Путь | Носитель | Содержимое |
|---|---|---|
| `/etc/config/roamd` | флеш | вся конфигурация |
| `/etc/roamd/id`, `/etc/roamd/id_rsa` | флеш | служебные SSH-ключи контроллера — Ed25519 и RSA: SSH-сервер части сборок OpenWrt не поддерживает Ed25519 |
| `/etc/roamd/members/<id>.crt`, `/etc/roamd/tokens/<id>` | флеш | сертификат и токен канала управления узла |
| `/etc/roamd/pkg.crt` | флеш | закреплённый сертификат своего репозитория пакетов; для репозитория проекта не нужен |
| `/var/run/roamd/pkg/<ветка>/<арх>/` | ОЗУ | кеш пакетов для узлов |
| `/etc/roamd-node.crt`, `/etc/roamd-node.key` | флеш узла | сертификат `uhttpd` для канала управления |
| `/tmp/roamd/mesh_log.jsonl`, `/tmp/roamd/clients.jsonl` | ОЗУ | журнал переходов и реестр клиентов |
| `/tmp/roamd/deps` | ОЗУ | итог подготовки зависимостей |
| `/tmp/roamd-pkg.lock` | ОЗУ | очередь операций roamd с пакетным менеджером устройства (`flock -n` с ожиданием до 120 с) |
| `/var/run/roamd/members/<id>.json`, `<id>.pkgsrc` | ОЗУ | последний отчёт узла, источник последней доставки |
| `/var/run/roamd/acquire/<task>` | ОЗУ | ход задачи |
| `/var/run/roamd/profile.sum` | ОЗУ | контрольная сумма последнего профиля: при её смене профиль раскатывается на все узлы |
| `/tmp/roamd/bh_scan` | ОЗУ узла | результат скана транспортных точек |
| `/var/run/roamd/candidates.json`, `selfcheck.json` | ОЗУ | результаты поиска и проверки обновлений |
| `/tmp/roamd-diag.log`, `/tmp/roamd-install.log` | ОЗУ | диагностика задач, журнал установки на узле |
